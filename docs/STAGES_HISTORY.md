# LabCRM — лабораторная CRM

Внутреннее приложение для лаборатории молекулярной селекции и ДНК-паспортизации растений: проекты и задачи, журнал работ, образцы, паспорта, склад, приготовление, методики, исходные блоки и хранение.

## Версия и достоверность документа

Репозиторий: `FBerensen/lab-crm`. Ветка: `feature/preparation-autoclaving`.
Проверяемый коммит: `6fa59d9d07ee68434ce4c30c36ec7699f61a350c` от 6 ноября 2026 года — `Save accepted LAB_CRM updates through stage 8Z`.

Описание этапов ниже сверено с доступными исходниками, тестами и историей коммитов этой версии. Оно описывает реализованные сценарии, но не является актом приёмки или заявлением об успешном запуске всех тестов.

Для этапов 1–5 последовательность подтверждается отдельными коммитами и модулями тестовых запусков. Доработки 5Б, 6 и 7 попали в накопительный коммит; отдельные даты их приёмки по этой истории не устанавливаются. Описывается их состояние в выбранном коммите с учётом последующих изменений этапа 8, а не побайтовое состояние старых поставок.

По предоставленному владельцем выводу рабочей установки миграции `0001`–`0023` отмечены как применённые, Django check прошёл без замечаний. Это не заменяет регрессионную проверку, сверку кода контейнера и восстановление копии. В ходе подготовки README Docker и тесты не запускались.

## Технологии и сервисы

- Python 3.12, Django 5.2, PostgreSQL 17.
- psycopg, Gunicorn, WhiteNoise, openpyxl, defusedxml.
- Docker Compose: `db`, `web`, `scheduler`.
- Интерфейс Django Admin с лабораторными формами и навигацией.

Адрес: `http://localhost:8000/admin/`. Web опубликован на `127.0.0.1:8000`. Данные PostgreSQL — в томе `postgres_data`.

Исходники копируются в образ. В проверенном Compose рабочая папка не подключена к web как bind-mount: изменение локального файла и обычный перезапуск не устанавливают новый код.

## Первоначальная установка

Только для новой установки с новой базой. Существующую систему не разворачивать заново поверх рабочей базы.

1. Подготовить Docker Engine / Docker Desktop и Docker Compose.
2. Получить ветку `feature/preparation-autoclaving`; для воспроизведения документа использовать указанный коммит. Не считать `main` эквивалентом этой версии.
3. Создать `.env` в корне проекта, исключить секреты из Git и контекста передаваемых архивов/образов.

```dotenv
DJANGO_SECRET_KEY=REPLACE_WITH_PRIVATE_RANDOM_SECRET
DB_PASSWORD=REPLACE_WITH_PRIVATE_DATABASE_PASSWORD
POSTGRES_ADMIN_PASSWORD=REPLACE_WITH_DIFFERENT_ADMIN_PASSWORD
ALLOWED_HOSTS=localhost,127.0.0.1
TIME_ZONE=Europe/Moscow
COOKIE_SECURE=0
```

Заглушки заменить до запуска. `COOKIE_SECURE=0` относится к локальному HTTP; HTTPS настраивается отдельно.

```bash
docker compose up --build -d
docker compose ps -a
docker compose logs --tail=80 web scheduler
docker compose exec web python manage.py createsuperuser
```

При старте web выполняются `migrate --noinput`, `bootstrap`, `collectstatic --noinput`, затем Gunicorn.

`bootstrap` создаёт группы, но не пользователей и не назначает индивидуальные разрешения. Администратор создаётся интерактивно, паролей по умолчанию нет. Скрипт новой базы создаёт роль `labcrm` без SUPERUSER, CREATEDB и CREATEROLE.

## Запуск, остановка, обновление

Из корня приложения:

```bash
docker compose start
docker compose ps -a
docker compose exec web python manage.py check
docker compose exec web python manage.py showmigrations lab
docker compose logs --tail=80 web scheduler
```

Остановка: `docker compose stop`. Не использовать `docker compose down -v` для выключения: удаляются тома.

Web healthcheck проверяет страницу входа, а не весь лабораторный процесс. Отдельный healthcheck scheduler не задан.

Перед обновлением:

1. Зафиксировать коммит, локальные изменения и миграции.
2. Сохранить код, Compose, защищённую копию `.env` и базу.
3. Проверить обновление на отдельной базе с существующими данными.
4. Выполнить соответствующие тесты и регрессию.
5. Согласовать окно без пользователей и других писателей.
6. Остановить запись и создать свежую копию базы.
7. Применить проверенный порядок сборки, миграций и пересоздания сервисов.
8. Проверить данные, интерфейс и фоновые задания.

Запуск нового web автоматически применяет миграции. Поэтому `docker compose up --build -d` не является безопасной предварительной проверкой рабочей базы.

Не применять старые установщики этапов поверх принятого 8З без проверки совместимости. Универсальный сценарий перехода с любой старой версии не заявляется. Не использовать `--fake`, удаление томов или обход контрольных проверок. Возврат только старого кода после изменения схемы не считается полноценным восстановлением.

## Роли

Для входа нужны «Активный» и «Статус персонала». Обычным сотрудникам не выдавать статус суперпользователя.

Группы: `Руководители`, `Склад`, `Исполнители`, `Стажёры`. Права зависят также от операции, состояния объекта и назначения сотрудника.

- Проверку результата задачи выполняет назначенный проверяющий, не исполнитель.
- Допуск приготовления: руководитель/администратор либо исполнитель с `lab.approve_preparation`; остальные проверки партии сохраняются.
- Стажёр не получает самостоятельный допуск. Сочетание стажёра с исполнителем/руководителем конфликтует в механизме допуска; суперпользователь обрабатывается отдельно.
- Отметку обработки руководитель/администратор может выполнять в предусмотренных сценариях; исполнитель/стажёр — для собственного приготовления.
- Проведение расхода журнала: руководитель либо пользователь с `lab.post_worklog_expense`, если нет группы `Стажёры`.
- Группа «Склад» сама по себе не равна праву проводить расход журнала.

Использовать точное имя `Стажёры`. Подсистема допуска также распознаёт `Стажеры`, но проверка расхода — только вариант с «ё». Эти имена нельзя считать взаимозаменяемыми настройками.

Базовые административные классы разрешают чтение активным сотрудникам со статусом персонала. Полная изоляция чтения по проектам не заявляется. Политика экспорта требует отдельной проверки.

## Базовые рабочие процессы

Задача имеет один проект, исполнителя, проверяющего, срок и этап лабораторной работы. Проба может входить в несколько проектов. Лабораторные этапы задачи — получение материала, выделение ДНК/РНК, ПЦР и т. п. — не являются номерами этапов разработки приложения.

Состояния меняются событиями. Принять, возобновить и передать результат должен сам исполнитель. Остановка требует причины, ответственного, следующего действия и даты. Передача другому исполнителю возвращает «Назначено». Повтор создаёт связанную новую задачу. Изменение срока требует пояснения.

Журнал фиксирует работу и фактическую дату отдельно от времени внесения; это не табель. Исправление текста — отдельная запись, а не автоматическая отмена расхода.

В карточке партии положительное начальное количество оформляется поступлением автоматически. Не дублировать его вручную. Резерв уменьшает свободное количество; расход из резерва уменьшает остаток и резерв своей задачи. Количество ручной операции вводится в единице партии. После движений единицу нельзя менять.

Приготовление: расчёт и подбор → черновик → фактические данные → необходимое подтверждение → проверка готовности → проведение → обработка и допуск. Сохранение не равно списанию, подтверждение факта не равно допуску. При расходе готовой партии компоненты повторно не списываются.

Рецептуры, режимы и критерии качества определяет утверждённый СОП, а не CRM.

## Подробное описание этапов 1–7

### Этап 1. Группировка интерфейса и представление приготовлений

Назначение: сделать существующий административный интерфейс понятнее без введения новых прав и складских действий.

Реализовано:

- Модели сгруппированы по рабочим направлениям; тестируется порядок «работа → образцы → склад → приготовление».
- Сохраняются разрешения и доступные модели; неизвестная новая модель не должна исчезнуть из меню.
- Убираются лишние завершающие нули в представлении чисел; отсутствующее значение показывается отдельно.
- Приготовление отображается через наименование, дату, объём и сотрудника.
- Плановый объём непроведённой записи обозначается как план, не как фактический выход.
- Для исторической записи сохраняется её исходная единица.
- При отсутствии полного имени используется имя пользователя; отсутствие исполнителя показано явно.

Основные файлы: `lab/admin_navigation.py`, `lab/presentation.py`.
Проверки: `lab/test_ui_stage1.py`.
Исторический коммит: `e19562f` — `Group admin navigation and simplify preparation display`.

Граница: это представление существующих данных; группировка меню не создаёт разрешений и не меняет остатки. В этапе 8Б навигация дополнительно расширена.

### Этап 2. Роли допуска и отметка автоклавирования

Назначение: разделить выполнение обработки, её регистрацию и разрешение использовать готовую партию.

Реализовано:

- Классификация пользователя: администратор, руководитель, исполнитель, стажёр, конфликт ролей или отказ.
- Руководитель/администратор имеет право допуска; исполнитель — при наличии `lab.approve_preparation`.
- Стажёр не получает право допуска; конфликт стажёра с исполнителем/руководителем не трактуется как повышение прав.
- Исполнитель и стажёр могут отметить обработку собственного приготовления; руководитель/администратор имеет отдельные полномочия.
- Отметка требует явного подтверждения обработки всей партии.
- Фиксируются автор и время обработки; штатная форма не снимает и не перезаписывает отметку.
- До проведения предлагается сначала провести приготовление.
- Историческая запись без достоверного требования обработки обозначается как требующая отдельной проверки.
- Отметка обработки не является допуском и не повторяет складские операции.

Основные файлы: `lab/preparation_access.py`, `lab/preparation_stage2_admin.py`, методы `Preparation`.
Проверки: `lab/test_preparation_stage2.py`, `lab/stage2_test_runner.py`.
Исторический коммит: `0fcc4f5` — `Add role-based preparation approval and autoclaving completion mark`.
Миграция: `0009_preparation_self_approval_autoclaving_mark`.

Граница: право допуска не отменяет проверки обработки, годности и состояния партии. Независимость проверки результата задачи — другое правило. Старый абсолютный запрет собственного допуска не описывает все роли этой версии.

### Этап 3. Мастер приготовления по протоколу

Назначение: провести пользователя от выбора рецептуры к сохранению непроведённого приготовления с явно введёнными фактами.

Реализовано:

- Выбор активного протокола активного продукта.
- Плановый объём и пресеты 50, 100, 200, 250, 500, 800, 1000 мл; допускается ввод своего объёма.
- Пересчёт рецептуры и количества в единице выбранной складской партии.
- Выбор допустимых допущенных непросроченных партий со свободным остатком.
- Предупреждение, если план превышает свободный остаток.
- Отдельный ручной ввод фактического расхода и фактического выхода: план не подставляется в факт автоматически.
- Для сохранения требуются фактический выход, категория и место готовой партии, выбранные партии и расходы компонентов.
- Проверки даты, срока годности и совместимости единиц.
- Подписанный расчёт связан с пользователем, протоколом, объёмом и отпечатком рецептуры; изменение исходных условий требует перерасчёта.
- Повтор одного сохранённого запроса открывает прежний черновик, а не создаёт второй.
- Сохраняются приготовление и строки компонентов без списания; проведение выполняется отдельным действием.

Основной файл: `lab/preparation_wizard.py`.
Проверки: `lab/test_preparation_wizard.py`.
Прямая привязка к этапу: `configure_admin` устанавливает `_lab_preparation_stage3`; `lab/stage3_test_runner.py` включает тесты мастера.
Исторический коммит: `da718a4` — `Add protocol-based preparation wizard`.

Граница: этот мастер не тождествен черновику 7В. Мастер сохраняет отдельно введённые факты в непроведённую запись; этап 7В умеет сохранить только план подбора без заполненного фактического выхода.

### Этап 4. Иерархия хранения и содержимое места

Назначение: связать физическое хранение образцов и складских продуктов со справочником, сохранив старые сведения.

Реализовано:

- Родительское место хранения и запрет циклов иерархии.
- Ссылка образца на место из справочника.
- Сохранение прежнего текстового места в `original_location`.
- Просмотр содержимого самого места либо вместе с вложенными местами.
- Счётчики непосредственно размещённых складских карточек и образцов.
- Поиск, отдельная пагинация образцов и партий, переходы в карточки.
- По умолчанию скрыты складские карточки с нулевым остатком; их можно включить.
- Отдельный счётчик и переход к образцам без привязки к справочнику.
- Управление местами доступно руководителю/администратору по проверке роли.
- Новая карточка образца требует место; активные места доступны для выбора, текущее значение существующей карточки сохраняется в допустимом наборе формы.

Основные файлы: `lab/storage_support.py`, `lab/storage_stage4_admin.py`, модели `StoragePlace` и `Sample`.
Проверки: `lab/test_storage_stage4.py`, `lab/test_storage_upgrade.py`.
Миграции: `0010_storage_hierarchy_sample_locations`, `0011_link_sample_storage_locations`.
Исторический коммит: `eaa5497` — `Add storage contents and sample location links with split migrations`.

Граница: исходные блоки добавлены в хранение позже, на этапе 8. Изменение места не является расходом.

### Этап 5. Список серий перед отдельными образцами

Назначение: начинать работу с обзора серий, не теряя плоский реестр и обычные фильтры.

Реализовано:

- При открытии списка без параметров сначала показывается обзор серий.
- По каждой серии считаются образцы, различные проекты, различные места и образцы без места.
- Поиск серии и постраничный вывод по 50 серий.
- Переход к точному составу выбранной серии.
- Режим всех образцов, обычный поиск и фильтрация остаются доступны.
- Навигационный параметр `all_samples` отделён от ORM-фильтров.
- Подсчёт образцов не должен умножаться из-за нескольких проектных связей.

Основной файл: `lab/sample_series_stage5.py`.
Проверки: `lab/test_sample_series_stage5.py`.
Исторический коммит: `380b47c` — `Show sample series before individual samples`.

Граница: серия — способ организации реестра; она не заменяет карточки и не создаёт складских операций. Подсчёт по `projects` отражает совместимость с этапом 8А.

### Подэтап 5Б-1. Сведения об отборе и получении пробы

Реализовано:

- Тип пробы: «генотип» или «bulk-проба»; это не то же самое, что тип материала ДНК/РНК/ткань и т. п.
- Часть растения, место отбора, дата отбора и дата получения в лабораторию.
- Неизвестные даты остаются пустыми; сегодняшняя дата не подставляется автоматически.
- Будущие даты отклоняются; получение не может быть раньше отбора.
- Поля присутствуют в карточке и пакетной форме; для дат подключены календарные элементы.
- Старые образцы получают неизвестные, а не вымышленные значения.

Файлы: `lab/sample_dates.py`, `lab/sample_stage5b_admin.py`; тесты `lab/test_stage5b1.py`.
Миграция: `0012_sample_collection_fields`.

### Подэтап 5Б-2. Паспорт материала

Реализовано:

- Отдельная сущность `MaterialPassport`: номер каталога ВИР, вид и происхождение.
- Связь с паспортом у образца необязательна.
- Пустой паспорт не принимается: хотя бы одно содержательное поле требуется.
- Пробелы по краям полей нормализуются.
- Номер каталога ВИР не объявлен уникальным идентификатором паспорта.
- В карточке образца представлены паспортные поля; в пакетной форме предусмотрен выбор паспорта.
- Для связи используется защита удаления; удаление паспортов через административный интерфейс отключено.

Файлы: `lab/material_passport_admin.py`, модель `MaterialPassport`; тесты `lab/test_stage5b2.py`.
Миграция: `0013_material_passport`.

Смежное расширение: паспортный Excel реализован в `lab/passport_excel.py`, проверки — `lab/test_passport_excel.py`. Это отдельный формат от Excel исходного блока этапа 8Г. Точное историческое буквенное обозначение этой доработки не устанавливается по одному имени файла.

### Этап 6А. Фактический расход через журнал

Назначение: связать складское списание с конкретной работой и отделить автора работы от подтверждающего сотрудника.

Реализовано:

- Строки расхода у записи журнала и заявка состояния расхода.
- Режимы расхода свободного остатка или резерва соответствующей задачи.
- Ожидающий расход не меняет складской остаток до проведения.
- Стажёр не проводит расход самостоятельно.
- Проверяются полномочия подтверждающего сотрудника, дата, пробы задачи и соответствие строк складским движениям.
- Перед проведением блокируются журнал, заявка, строки и партии.
- Весь набор проводится атомарно: ошибка не должна оставить частичное списание.
- Фиксируются автор работы, проводящий сотрудник и созданные движения.
- Повтор уже проведённой заявки не создаёт новые движения.
- Проведённые строки нельзя править как ожидающий расход; нужна отдельная корректировка.

Файлы: `lab/worklog6.py`, `lab/worklog6_admin.py`, `lab/worklog6_permissions.py`.
Проверки: `lab/test_stage6a.py`.
Миграции: `0014_worklog_expenses`, `0015_worklog_expense_permissions`.

Граница: отражение расхода в задаче не является вторым списанием; исправление текста журнала не отменяет автоматически движения. Часть ограничений закрытия введена следующим подэтапом 6Б-2.

### Подэтап 6Б-1. Наличие и ожидающий расход

Назначение: показать обеспеченность уже внесённого ожидающего расхода, а не универсальный прогноз всех будущих работ.

Реализовано:

- Физический остаток, резерв, свободное и доступное количество.
- Доступное свободное количество равно свободному остатку допущенной непросроченной партии; для недопущенной/просроченной — ноль.
- Ожидающий расход свободного остатка сравнивается с доступным количеством.
- Расход из резерва сравнивается отдельно с резервом каждой задачи.
- Проверяется согласованность поля резерва с историей резервных движений.
- Предупреждения: просрочка, отсутствие допуска, нулевой остаток, минимум, несогласованный резерв и нехватка.
- Поиск и фильтры категории, места и проблемных состояний.
- Страница только читает данные: не резервирует и не списывает.

Файл: `lab/stock_availability.py`; тесты `lab/test_stage6b1.py`.
Миграция: `0016_stock_availability`.

Граница: на странице прямо исключены плановые потребности будущих задач и рецептур. Ожидающий расход не является автоматическим резервом. Проведённый расход не вычитается повторно.

### Подэтап 6Б-2. Методики, выполнения и планы материалов

Реализовано:

- `LaboratoryProtocol`, конкретное `LaboratoryProtocolRun` и `TaskMaterialPlan`.
- Запуск выполнения из черновика при задаче «В работе».
- Проверка активной версии методики и допустимости выбранных проб.
- При запуске сохраняются состав проб в аудите и снимок кода, названия, версии, вида и инструкции методики.
- Запись журнала должна соответствовать задаче и выполнению; пробы — входить в допустимый состав.
- До начала выполнения журнал к нему не привязывается; новое выполнение/расход ограничиваются состояниями процесса.
- Закрытие требует результата, допустимой даты и проведённого расхода связанных работ.
- Закрытие само не списывает материалы.
- Подтверждение задачи запрещено при незакрытых выполнениях или неподтверждённом расходе.
- Передача задачи блокируется при незакрытых выполнениях.
- План сравнивается с фактическим расходом, остаточной потребностью, своим резервом, непокрытой частью и перерасходом.
- Используются актуальные партии; несовпадение единицы и несогласованный резерв учитываются как проблемы.

Файлы: `lab/lab6b2_services.py`, `lab/lab6b2_admin.py`, соответствующие модели.
Проверки: `lab/test_stage6b2.py`.
Миграция: `0017_laboratory_protocols_and_plans`.

Граница: план не создаёт резерв и не является фактом. Снимок лабораторной методики не нужно путать с отдельной рецептурой приготовления.

### Этап 7А. Калькулятор приготовления

Назначение: рассчитать потребность на выбранный конечный объём и показать состояние разрешённых исходных партий.

Реализовано:

- Масштабирование количеств относительно базового объёма протокола.
- Преобразование совместимых единиц внутри массы или объёма.
- Рассмотрение разрешённых партий с проверкой допуска, годности и свободного количества.
- Предупреждения по наличию и повторное получение текущего состояния.
- Раздельное обращение с фиксированной дозировкой и «довести до конечного объёма».
- Информационный расчёт без сохранения приготовления, резерва или расхода.

Файл: `lab/preparation_calculator.py` и методы компонентов протокола.
Проверки: `lab/test_stage7a.py`.
Миграция: `0018_preparation_calculator`.

Граница: калькулятор не вычисляет химическую приемлемость, не подтверждает pH/концентрацию измерением и не удерживает материалы за расчётом.

### Этап 7Б. Подбор исходных партий

Реализовано:

- Выбор одной или нескольких партий для компонента.
- Количество вводится в складской единице партии, не более четырёх десятичных знаков.
- Фиксированный компонент должен быть набран точно: недостаток и превышение отклоняются без неявного допуска.
- Повтор пары «компонент + партия» запрещён.
- Общий расход одной партии суммируется по всем компонентам и сравнивается со свободным остатком.
- Для доведения объёма можно оставить количество неопределённым; такой набор не считается полностью заполненным.
- Ручной расход растворителя не доказывает достигнутый конечный объём.
- Неизвестные или повторно переданные поля формы отклоняются.
- Доступность проверяется заново; набор сам по себе не хранится как складская операция.

Файл: `lab/preparation_allocation.py`.
Проверки: `lab/test_stage7b.py`.

Граница: предпросмотр не создаёт приготовление, резерв или списание. Сохранение выполняется отдельным сценарием 7В.

### Этап 7В. Сохранённый подбор и подтверждение фактов

Реализовано:

- Сохранение прошедшего проверку плана подбора вместе с метаданными будущей партии.
- Снимок рецептуры, партий, единиц и количеств; отпечатки исходных условий и запроса.
- Плановые строки `PreparationDraftLine` отделены от фактических `Component`.
- У нового черновика из подбора фактический выход не заполнен; складские движения и готовая партия не создаются этим действием.
- Подписанный запрос связан с пользователем и временем; повтор того же запроса с теми же параметрами не создаёт дубль.
- Тот же ключ с другими параметрами отклоняется.
- Перед сохранением повторно проверяются рецептура, единицы, партии, категория и место.
- Фактические данные требуют явного подтверждения с отпечатком просмотренного состояния.
- Проверяются полнота расхода, включая растворитель, актуальная рецептура, объём и суммарная доступность партий.
- Изменение фактов после подтверждения делает старое подтверждение недостаточным.
- Повторное неизменённое подтверждение не создаёт дополнительный аудит.

Файлы: `lab/preparation_drafts.py`, `lab/preparation_drafts_admin.py`.
Проверки: `lab/test_stage7v.py`.
Миграция: `0019_preparation_draft_selection`.

Граница: подтверждение фактов не проводит приготовление и не допускает партию. Дополнительный барьер подтверждения относится к записям с сохранённым подбором 7В, а не автоматически ко всем историческим приготовлениям.

### Этап 7Г. Предпроверка готовности к проведению

Реализовано:

- Отчёт о виде операции, активности рецептуры и продукта.
- Проверки положительных планового/фактического объёмов и актуальности подтверждения 7В.
- Проверки категории, места, срока годности и параметров будущей партии.
- Новая карточка результата проверяется в памяти, без её сохранения.
- Для существующего результата проверяются нулевые остатки/резерв и отсутствие складской истории.
- Проверяются единицы и точная представимость выхода.
- Проверяются фактические строки, полнота рецептуры и расход растворителя.
- Расход одной партии суммируется по компонентам; проверяются допуск, годность и свободный остаток.
- Для проведённого приготовления показывается, что повторное проведение недоступно; израсходованные источники не трактуются заново как требование повторного проведения.

Файлы: `lab/preparation_readiness.py`, `lab/preparation_readiness_admin.py`.
Проверки: `lab/test_stage7g.py`.

Граница: результат действителен на момент проверки. Предпроверка не резервирует партии, не проводит и не допускает приготовление; фактическая операция повторно проверяет условия.

### Этап 7Д. Список приготовлений и состояния

Реализованы состояния представления:

Файл: `lab/preparation_list7d.py`.
Проверки: `lab/test_stage7d.py`.

Граница: этап списка не является разрешением на проведение. Запись подтверждения не доказывает его актуальность; зарегистрированный допуск не заменяет текущую проверку партии на складе. Установка этого расширения требует уже подключённой предпроверки 7Г: буквенный порядок не является универсальным порядком установки.

### Как проверять покрытие этапов

Указанные тестовые файлы описывают проверки, но их наличие не означает успешного прогона. Полные результаты принимаются для конкретного коммита и окружения. Имена тестовых баз и исторические runner-модули имеют защитные ограничения; не запускать их на рабочей базе и не убирать защиту ради прохождения.

### Образцы и несколько проектов

Основная принадлежность — `Sample.projects` через `SampleProjectMembership`. Старое `Sample.project` оставлено для технической совместимости, не является актуальным «главным проектом». Для новых интеграций и фильтров использовать канонические связи.

Для непосредственной пары «родитель — потомок» требуется общий проект, но все проекты не обязаны совпадать. Автоматического распространения по всей цепочке нет. Задача имеет один проект; выбранная проба должна входить в него. Общий проект не является проверкой отсутствия циклов происхождения.

### Исходные блоки

Схема A1–H12, 96 позиций. Типы: зарегистрированная проба, водный контроль, незарегистрированная подпись; пустота — отсутствие позиции.

Подпись не создаёт пробу автоматически. Одна проба может размещаться повторно. Очистка позиции не удаляет пробу. Водный контроль содержит 0 мкл ДНК; неизвестная вода отличается от явного нуля. Изменение общих настроек не должно переписывать прежние индивидуальные объёмы.

Изменения защищены версией блока. Схема сама не подтверждает опыт и не списывает склад.

### Excel блока

Импорт — в выбранный существующий блок, без создания новых проб и блоков. Загрузка → предпросмотр → подтверждения → применение. Режимы: заполнить пустые или обновить указанные; очистка включается отдельно.

Предпросмотр создаёт техническую запись, но не меняет блок и лунки. Срок 15 минут; применение связано с пользователем и актуальной версией. Повтор применённого запроса не дублирует изменения. Свободные подписи и очистка требуют предусмотренных подтверждений.

Полный экспорт содержит технические листы типов. Их удаление может потерять различие контроля и буквальной подписи. Старый однолистовый формат распознаётся по отдельным правилам.

Разрешён ограниченный формат XLSX; формулы и небезопасная структура отклоняются. Паспортный Excel — другой механизм. Автоматическая очистка истёкших технических предпросмотров требует отдельной политики.

### Содержимое и размещение

Страница места показывает образцы, продукты и блоки, включая вложенные места по выбору. Есть поиск, фильтры, настройка столбцов, отдельная пагинация 25/50/100, заполненность блоков и переходы в схему.

Отображение мл/л или г/кг в удобном масштабе не меняет складскую единицу и остаток.

«Разместить материал»: выбрать активное место → тип объекта → существующий объект → проверить прежнее/новое место → подтвердить целиком. Нужны права просмотра и изменения. Подтверждение связано с пользователем и местом, действует 15 минут. Изменение прежнего места отклоняет устаревший запрос; для блока проверяется версия.

Размещение не создаёт материал, не делит партию и не меняет остаток/резерв. Место блока не означает автоматического перемещения связанных карточек проб.

## Отчёты и почта

С пятого числа первого месяца квартала scheduler раз в час создаёт черновик за предыдущий квартал. После простоя — последний положенный период, не все пропущенные. Пример ручного формирования:

```bash
docker compose exec web python manage.py quarter_report 2026 3
```

Один сохранённый отчёт на квартал; повторное формирование его не перезаписывает. Поздние исправления автоматически не обновляют сохранённый документ.

События выбираются по времени внесения; работы, движения и приготовления — по фактической дате. Снимки задач и склада показывают момент формирования, не конец квартала. Это не полный научный отчёт по всем сущностям этапа 8.

Почтовое вложение — JSON. PDF получают через печать браузера; автоматический PDF планировщика не заявлен.

Настройки: `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS`, `DEFAULT_FROM_EMAIL`, `REPORT_RECIPIENTS`. После изменения окружения требуется корректное пересоздание сервисов с учётом миграций при старте web.

Отправляются утверждённые неотправленные отчёты. `sent_at` означает приём SMTP, не доставку адресату; авария между отправкой и записью отметки допускает повтор.

## Резервное копирование в PowerShell

Из корня проекта, для текущих имён сервисов и базы. Перед согласованной предобновительной копией остановить всех писателей данных, оставив db.

```powershell
& {
    $ErrorActionPreference = "Stop"
    $stamp = Get-Date -Format "yyyyMMdd-HHmmss"
    $backupDir = Join-Path (Get-Location).Path "backups"
    New-Item -ItemType Directory -Path $backupDir -Force | Out-Null
    $containerBackup = "/tmp/labcrm-$stamp.dump"
    $localBackup = Join-Path $backupDir "labcrm-$stamp.dump"
    docker compose exec -T db pg_dump -U postgres -d labcrm -Fc -f $containerBackup
    if ($LASTEXITCODE -ne 0) { throw "pg_dump failed" }
    docker compose cp "db:$containerBackup" $localBackup
    if ($LASTEXITCODE -ne 0) { throw "Backup copy failed" }
    docker compose exec -T db pg_restore --list $containerBackup | Out-Null
    if ($LASTEXITCODE -ne 0) { throw "Backup TOC check failed" }
    Get-Item -LiteralPath $localBackup | Select-Object FullName, Length
}
```

Оглавление не заменяет пробного восстановления. Хранить копию вне компьютера, `.env` — отдельно и защищённо. Восстанавливать для проверки в отдельную базу с совместимой версией приложения. Не восстанавливать поверх рабочей базы без плана. Автоматическое копирование по расписанию в показанном Compose отсутствует.

## Приёмка релиза

Нужны полный безопасный прогон тестов, проверка обновления на существующих данных и восстановление. Не использовать старые ожидаемые количества тестов как счётчик нового релиза.

Проверить роли/стажёра, события задач, журнал/расход, остатки/резервы и конкуренцию, серию/паспорт/Excel, методики/планы, расчёт/подбор/черновик/факт/проведение/допуск, все типы позиций, повторные/устаревшие запросы, хранение/размещение, отчёты/SMTP и восстановление.

## Ограничения и технический долг

- Наличие кода и тестов не равно успешной приёмке.
- Административный интерфейс, без заявленной полной изоляции чтения по проектам.
- Неодинаковая обработка вариантов имени роли стажёра требует унификации.
- Аудит не является криптографической неизменяемостью и не защищает от администратора БД.
- Полное версионирование квартальных отчётов и автоматическая отмена всех ошибочных движений не заявлены.
- Нужно определить хранение технических предпросмотров Excel.
- Зависимости/образы требуют фиксации проверенных версий для воспроизводимости.
- В settings.py есть исторические повторные присваивания MIGRATION_MODULES; итог включает `lab.migrations`.
- Есть историческая настройка дополнительного `templates8b`; выбор шаблонов нужно проверять при чистом развёртывании.
- Вложения, приборы, штрихкоды, SSO, пользовательский сброс пароля и ограничение входа не входят в заявленный набор этого документа.
- Нагрузочная устойчивость, аудит безопасности и отраслевое соответствие не подтверждены.

Перед сетевой эксплуатацией обязательны HTTPS, проверенная конфигурация cookies/прокси, контроль доступа и экспорта, резервное копирование по расписанию и проверка восстановления.
