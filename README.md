# Лабораторная CRM — пилот 0.1

Статус: исходный комплект, автоматически не проверен.
Не предназначен для промышленной эксплуатации без приёмки.

## Установка

Нужны Docker Engine / Docker Desktop и Docker Compose.

    docker compose up --build -d
    docker compose exec web python manage.py createsuperuser

Открыть http://localhost:8000/admin/

Администратор создаётся интерактивно; паролей по умолчанию нет.
Первоначально слушается только 127.0.0.1.

## Роли

Пользователей создаёт администратор в разделе пользователей.
Для входа включить «Активный» и «Статус персонала».
Не выдавать «Статус суперпользователя» обычным сотрудникам.

- Руководители: создание проектов и задач, передача, изменение сроков,
  повтор, проверка назначенных результатов, допуск партий, отчёты.
- Склад: создание партий и ручные складские операции.
- Исполнители: работа со своими задачами, журнал, подготовка партий.
- Суперпользователь: управление учётными записями и административный доступ.

В пилоте активные сотрудники с доступом к интерфейсу читают общий
реестр проектов, задач, проб, журналов и запасов.
Изоляции данных по отдельным проектам пока нет.
Назначенный проверяющий должен быть руководителем.
Исполнитель не может утверждать собственный результат.
Приготовивший партию не может сам её допустить.

## Первый сценарий

1. Создать два аккаунта сотрудников: исполнитель и проверяющий.
2. Проверяющему назначить группу «Руководители».
3. Создать проект.
4. При необходимости зарегистрировать пробу.
5. Создать задачу: исполнитель, проверяющий, срок, этап.
6. Войти исполнителем.
7. В разделе «Действия и история задач» создать «Принять в работу».
8. Записать работу в журнал, указав фактическую дату.
9. Для остановки создать действие с причиной, ответственным,
   следующим действием и ожидаемой датой.
10. Для передачи результата создать «Передать результат на проверку».
11. Войти назначенным проверяющим и подтвердить или вернуть результат.

Изменения состояния выполняются через события, не редактированием задачи.
Повтор создаёт новую связанную задачу.
Срок меняется событием «Изменить срок» с обязательным пояснением.
Смена этапа фиксируется новым событием с полем «Новый этап».

Журнал показывает внесённые работы, а не автоматически подтверждённую
посещаемость или количество отработанных часов.
Ошибочная запись исправляется новой записью со ссылкой на исходную.

## Склад

Сначала создать карточку партии с нулевым остатком.
Затем внести «Поступление».
Резерв уменьшает свободный, но не физический остаток.
Расход из резерва уменьшает и физический остаток, и резерв этой задачи.
Автоматической конвертации мл/мкл или г/мг нет.
Количество всегда вводится в единице конкретной партии.

Ручные движения создаёт склад или руководитель.
Исправление ошибочного движения требует согласованного компенсирующего
движения; автоматической процедуры отмены в этой версии нет.

## Приготовление и автоклавирование

1. Создать отдельную новую карточку готовой партии с нулевым остатком.
2. Создать «Подготовку партии».
3. Выбрать готовую партию, количество, дату и ссылку на утверждённый СОП
   либо идентификатор цикла.
4. В строках исходных партий указать фактические количества компонентов
   или необработанных расходников.
5. Сохранить: исходные количества списываются, готовая партия приходуется.
6. До допуска другим руководителем готовую партию нельзя расходовать.
7. Руководитель выбирает подготовку и действие «Допустить».

При последующем расходе готовой партии исходные компоненты не
списываются второй раз.

Программа не задаёт химические рецептуры, режимы автоклавирования
и критерии стерильности. Они должны быть определены утверждёнными
лабораторными СОП; допуск в CRM не заменяет их проверку.

## Отчёты

С пятого числа января, апреля, июля и октября создаётся черновик
за предыдущий квартал. Проверка выполняется раз в час.
После простоя автоматически создаётся только последний положенный
черновик. Более старые периоды формируются вручную.

Ручное формирование:

    docker compose exec web python manage.py quarter_report 2026 3

Один сохранённый отчёт на квартал. Существующий отчёт не перезаписывается.
Версионирование отчётов и автоматический учёт поздних исправлений
в ранее сформированном документе пока не реализованы.

События задач выбираются по времени внесения.
Работы, складские движения и подготовки — по фактической дате выполнения.
Фактическая дата и дата внесения показываются раздельно.

Текущие снимки задач и склада специально подписаны:
они отражают момент формирования, НЕ состояние на конец квартала.

Отчёт открывается в виде таблиц; печать браузера позволяет сохранить PDF.
Доступны JSON и CSV для отдельных реестров.
Автоматической генерации PDF-файла в планировщике нет.

Для почты заполнить EMAIL_HOST, EMAIL_PORT, EMAIL_HOST_USER,
EMAIL_HOST_PASSWORD, DEFAULT_FROM_EMAIL, REPORT_RECIPIENTS в .env.
Перезапустить web и scheduler.

Утверждённые неотправленные отчёты планировщик передаёт почтовому серверу.
Без настроенной почты и получателей рассылка не выполняется.
sent_at означает передачу SMTP-серверу, не доставку адресату.
При аварии после приёма SMTP, но до записи sent_at возможна повторная
отправка; гарантии exactly-once нет.

## Резервная копия

Из папки приложения:

    mkdir -p backups
    docker compose exec -T db pg_dump -U postgres -d labcrm -Fc > backups/labcrm.dump

Копию хранить также вне компьютера с CRM.
Секреты .env сохранять отдельно и защищённо.
Резервное копирование не запускается автоматически.

Для пробного восстановления в ОТДЕЛЬНУЮ базу:

    docker compose exec db createdb -U postgres -O labcrm labcrm_restore_test
    docker compose exec -T db pg_restore -U postgres -d labcrm_restore_test --no-owner < backups/labcrm.dump

Не восстанавливать поверх рабочей базы без отдельного плана.
Проверка восстановления в этой поставке не выполнялась.

## Обязательная приёмка

- Вход разных пользователей и отсутствие административных прав у исполнителя.
- Работа только назначенного исполнителя с приёмом и результатом.
- Независимость проверяющего.
- Остановка без обязательных данных отклоняется.
- Передача другому исполнителю требует повторного принятия.
- Повтор создаёт отдельную задачу.
- Нельзя израсходовать больше остатка.
- Нельзя использовать резерв чужой задачи.
- Две параллельные операции не создают отрицательный остаток.
- Подготовка списывает компоненты и создаёт ровно одну готовую партию.
- Расход готовой партии не списывает компоненты повторно.
- Просроченную или недопущенную партию нельзя расходовать.
- Проверка квартального периода, черновика, утверждения и SMTP.
- Восстановление резервной копии и сверка записей.

## Ограничения

- Не проводились запуск, нагрузочные испытания или аудит безопасности.
- Интерфейс первой версии — административный, не отдельный личный кабинет.
- Нет вложений, интеграции с приборами, штрихкодов и SSO.
- Нет отдельных уведомлений о каждой передаче задачи.
- Нет самостоятельного сброса пароля через настроенный пользовательский интерфейс.
- Нет ограничения частоты попыток входа.
- Нет разграничения чтения по проектам.
- Нет управления редакциями карточек проб и партий:
  после создания они доступны только для чтения.
- Изменения проектов отражаются в аудите как перечень изменённых полей,
  но старые и новые значения проекта целиком не сохраняются.
- Защита журналов от изменения действует через интерфейс приложения;
  это не криптографическая неизменяемость и не защита от администратора БД.
- Нет автоматической отмены ошибочных складских движений.
- Нет версионирования квартальных отчётов.
- Нет штатных миграций для дальнейших изменений схемы:
  перед обновлениями их нужно подготовить.
- Образы и зависимости указаны диапазонами, не зафиксированы хешами:
  после испытаний нужен воспроизводимый lock-файл.
- Не подтверждено соответствие отраслевым и регуляторным требованиям.

Перед сетевой эксплуатацией обязательны HTTPS, защищённые cookies,
ограничение входа, резервное копирование по расписанию, проверка прав,
тестирование конкурентных операций и обновление зависимостей.

Не открывать порт в интернет простым изменением привязки Compose.
